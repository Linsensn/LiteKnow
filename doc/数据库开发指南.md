
# 轻知(LiteKnow) 数据库开发指南

本系统采用 **Code-First** 模式。**核心原则：数据库结构的变化必须通过 Python 代码（Models）驱动，严禁任何成员手动在 Navicat 或命令行中执行 `CREATE TABLE` 或 `ALTER TABLE` 语句。**

**架构说明**：本项目采用“无云端、纯本地”的开发模式。每个开发人员的本地环境通过 Docker Compose 独立运行一个 MySQL 容器。数据库结构的版本演进，完全依靠 **Alembic 迁移脚本** 进行管理和同步。

### 0. 核心开发理念：全面拥抱 ORM
**严禁在业务代码中手写原生 SQL 语句（如 `INSERT INTO...` 或 `SELECT FROM...`）以及使用底层 `pymysql.connect` 裸连数据库！**
所有数据库交互必须通过 FastAPI 的依赖注入获取 `db` 会话，并使用 SQLAlchemy ORM 进行对象化操作。
* **结构定义**：通过定义继承 `Base` 的模型类（Class）来完成表结构设计，由 Alembic 自动翻译成 DDL。
* **增删改查**：在 Router 或 Service 层使用 `db.query(Model).filter(...)` 等对象化方法，兼顾开发效率与防止 SQL 注入风险。

### 1. 本地联调环境接入 (接入本地 Docker MySQL)

无需连接云端，只需确保本地环境配置正确即可。

1.  **配置环境变量**：请复制项目根目录下的 `.env.example` 并重命名为 `.env`（或直接修改现有的 `.env` 文件）。
    > 注意：`.env` 文件位于项目根目录 `/liteknow` 下。

    请在 `.env` 文件中配置本地数据库连接。由于 Docker 容器间的网络互通，`MYSQL_HOST` 填写 docker-compose 中定义的服务名（通常是 `mysql`）即可：
    ```ini
    # 指向 docker-compose.dev.yml 中定义的 MySQL 服务名
    MYSQL_HOST=mysql
    MYSQL_PORT=3306
    MYSQL_DATABASE=liteknow_dev
    
    # 本地开发统一使用 root 账号，密码与 docker-compose 文件中保持一致即可
    MYSQL_USER=root
    MYSQL_PASSWORD=root_password
    ```

2.  **拉起容器环境**：在项目根目录执行以下命令。此时 Docker 会自动拉取 MySQL 镜像并启动，同时拉起你的 FastAPI 后端。
    ```bash
    docker-compose -f docker-compose.dev.yml up -d
    ```
    *(注：如果首次启动，请检查 `docker ps`，确认 `liteknow-mysql-dev` 容器已处于 `Up` 状态)*

3.  **验证连接**：使用 **Navicat** 连接本地 MySQL（Host：`localhost`，端口：`3306`，用户名：`root`，密码：`.env` 中配置的 `MYSQL_PASSWORD`），看到 `liteknow_dev` 数据库即代表环境配置成功。

### 2. 日常开发流：如何修改数据库结构？

当开发人员需要增加一张新表或给现有表增加字段时，请严格遵循以下“五步走”闭环流程：

#### 第一步：编写/修改 Python 模型 (ORM)
在本地的 `backend/models/` 目录下修改或新增 SQLAlchemy 类。只定义表结构（Column），**不要在里面写任何增删改查的业务逻辑**。
```python
# 示例：定义模型类
from sqlalchemy import Column, Integer, String, Text
from database import Base

class QuestionBank(Base):
    __tablename__ = "questions_bank"
    id = Column(Integer, primary_key=True, autoincrement=True)
    question_text = Column(Text, comment="题目内容")
    difficulty = Column(Integer, comment="难度系数 1-5") # 新增字段示例
```

#### 第二步：在 `env.py` 中注册模型
**如果是新建了 Python 模型文件**，必须将其手动导入到 Alembic 的上下文中，否则 Alembic 会变成“瞎子”，导致生成的迁移脚本为空。

打开 `backend/migrations/env.py`，在获取 `metadata` 之前导入你的新模块：
```python
import sys
import os
sys.path.append(os.path.dirname(os.path.dirname(__file__)))

from database import Base 
# 必须在这里导入你编写了新表模型的模块，让 Alembic 能扫描到！
import models.questions_bank 

target_metadata = Base.metadata
```

#### 第三步：在容器内生成迁移快照
执行以下命令，让容器内的 Alembic 对比“代码模型”与“**本地 MySQL 数据库**”的差异，并在 `migrations/versions/` 下生成新的脚本文件。
```bash
# 注意必须使用 docker exec 进入后端容器执行！
docker exec -it liteknow-backend-dev alembic revision --autogenerate -m "add_question_difficulty"
```
*(成功标志：终端输出 `INFO [alembic.autogenerate.compare] Detected added column...`)*

#### 第四步：将变更应用到本地数据库
执行升级命令，将刚才生成的结构变动真实地刷入你**本地的 MySQL 数据库**中。
```bash
docker exec -it liteknow-backend-dev alembic upgrade head
```

#### 第五步：提交代码
确认本地数据库变更生效后，将修改的 **模型文件 `.py`**、**`env.py`** 和 **`migrations/versions/` 下新生成的脚本文件** 一并 `git add .`、`git commit` 并 `git push` 到 GitHub 远端仓库。

### 3. 团队同步规约：本地数据库时代的协作法则

与“共享云端数据库”不同，大家各自持有本地独立数据库，**绝对依赖迁移脚本**。请务必遵守以下协作法则：

* **全员同步原则（必需执行）**：当队友 A 提交了包含数据库模型变更的 PR 且被合并到 `dev` 分支后，**其他所有队友（包括 B、C 等）在拉取该最新代码后，必须严格在自己的本地环境中执行 `alembic upgrade head`**，以使自己的本地 MySQL 结构与之对齐。
  ```bash
  # 每次拉取 git pull 后，必须执行！
  docker exec -it liteknow-backend-dev alembic upgrade head
  ```

* **严防并发冲突（版本树分叉）**：严禁两名以上的开发人员（如 A 和 B）在各自未同步最新版本的情况下，同时基于旧版本各自生成并提交了 `revision` 迁移脚本。这会导致 GitHub 上出现版本树分叉（Heads 不唯一）。
  * **解决措施**：如果发生冲突，需先执行 `git pull` 拉取对方代码，然后进入容器执行 `docker exec -it liteknow-backend-dev alembic merge heads` 将两个分叉的头部合并成一个，之后再生成新的 `merge` 迁移脚本并提交。

* **禁止篡改历史**：`migrations/versions/` 目录下的每一个文件都是数据库进化的“DNA”。确保生成脚本前目录内没有多余的“空壳脚本”；**合并后**的历史脚本，严禁任何人私自删除或修改内容，否则将导致无法正确回滚或升级。
