# 轻知(LiteKnow) 基础开发与本地测试流程规范

为了保障开发团队的高效并行开发，所有开发人员在领取 GitHub Issue 后，必须严格遵循以下“五步走”标准化开发流。

> **⚠️ 项目环境特殊说明**：
> 1. **微信小程序端**：需使用微信开发者工具在本地运行。
> 2. **无云端共享数据库**：数据库（MySQL）在本地 Docker 容器中运行，数据库结构变更**必须**通过 Alembic 生成迁移文件并提交到 Git 仓库，以此保证团队数据库结构的一致性。

## 1. 准备工作：状态同步与建立分支

在开始写新代码前，必须清理掉历史遗留的已合并分支，确保基于最新的主干拉取专属开发分支。

* **第一步**：检查当前分支状态，确保没有未提交的更改（如果有，请先 Commit）。
  ```bash
  git status
  ```
* **第二步**：切换到团队开发主干，并清理之前已经合并完的旧任务分支（保持本地环境极简）。
  ```bash
  git checkout main
  # 强制删除已完成的旧分支（将 feat/xxx 替换为实际的历史分支名）
  git branch -D feat/backend-1
  ```
* **第三步**：拉取云端最新代码。
  ```bash
  git fetch
  git pull
  ```
* **第四步**：基于最新主干，创建并切换到你的专属任务分支，并立即推送到远端仓库。
  ```bash
  # 示例：后端新功能，关联任务编号 1
  git checkout -b feat/backend-1

  # 立即推送到云端并建立追踪关系 (仅首次创建分支时需要)
  git push -u origin feat/backend-1
  ```

## 2. 环境初始化

彻底废弃本地裸机 `pip install` 的做法。每次切换到新分支后，需通过 Docker 体系同步基础环境。

* **前提条件：开启本地 Docker 引擎**
  在执行后续与容器相关的任何命令前，**请务必确保本地电脑上的 Docker Desktop 软件已打开**并处于正常运行状态。

* **步骤一：配置本地环境变量 (仅首次或配置更新时执行)**
  复制项目根目录下的 `.env.example` 并重命名为 `.env`。
  由于本地没有云数据库，**.env 文件中的数据库连接地址必须指向本地的 Docker 内部网络**（例如：`DATABASE_URL=mysql+pymysql://root:password@mysql:3306/liteknow`，其中 `mysql` 是 Docker Compose 中定义的服务名）。

* **步骤二：环境依赖同步与镜像构建**
  本地开发已通过目录挂载实现代码热重载，常规的业务逻辑修改无需重新打包容器。但在涉及环境底层变更时，请按以下两种场景处理：
  * **场景 A（被动同步）**：拉取最新代码后，发现队友更新了环境依赖并添加了新的 Python 库。此时必须重新构建后端镜像。
    ```bash
    # 构建/拉取MySQL、Redis等基础设施镜像
    docker-compose -f docker-compose.dev.yml pull
    ```
  * **场景 B（主动变更）**：你在本次开发任务中，主动引入了新的 Python 第三方库并将其写入了 `requirements.txt`。此时必须在本地重新构建后端镜像。
    ```bash
    # 仅重新构建后端服务镜像
    docker-compose -f docker-compose.dev.yml build backend
    ```

## 3. 核心开发：严格遵循注释规范

进入业务开发阶段。为了保障后续软件著作权申请，所有新增代码必须包含规范的注释。

* **文件头注释**：新建文件时，使用 VS Code 快捷键 `header` + `Tab` 生成版权与作者信息。
* **函数级注释**：编写核心方法时，使用快捷键 `fdoc` + `Tab` 生成标准的参数、返回值及异常抛出声明。
* **代码热重载**：因为 `docker-compose.dev.yml` 配置了目录挂载（Volumes），你修改并保存的任何 Python 文件和前端代码都会实时同步到容器内部并自动热重载，无需重启容器。

## 4. 本地联调：一键拉起容器化环境

全面废弃手敲 `uvicorn` 命令，统一交由 Docker Compose 进行微服务编排。在提交代码前，开发人员必须在本地完成容器化验证。

* **第一步：启动全栈测试环境**：
  在项目根目录执行以下命令，一键拉起后端 (FastAPI)、MySQL、Redis 等所有关联组件。
  ```bash
  docker-compose -f docker-compose.dev.yml up -d
  ```

* **第二步：执行 Alembic 数据库版本迁移 (核心必做)**
  由于项目采用 **无云端数据库** 模式，每次拉取最新代码后（或修改了数据库模型后），**必须**执行 Alembic 升级，以确保本地 MySQL 与代码中的 Model 保持一致。
  > 注意：当你修改了 `models.py` 后，需要在容器内使用 `alembic revision --autogenerate -m "描述"` 生成迁移文件，并将生成的 `/migrations/versions/*.py` 文件提交到 Git 仓库，保证团队同步。
  ```bash
  # 执行数据库迁移
  docker exec -it liteknow-backend-dev alembic upgrade head
  ```

* **第三步：挂起后端日志 (按需执行)**
  想要在控制台实时监控后端状态，请执行此命令：
  ```bash
  docker logs -f liteknow-backend-dev
  ```

* **第四步：服务入口与访问**：
  * **微信小程序调试**：打开 **微信开发者工具**，导入本项目的小程序前端代码目录。在工具右上角详情 -> 本地设置中，勾选 **“不校验合法域名、web-view（业务域名）、TLS版本以及HTTPS证书”**。此时小程序可以通过 `http://localhost:8000` 访问本地的 FastAPI 后端接口。
  * **后端 API 规范测试 (主力)**：打开 **Apifox**，将运行环境切换为 `本地环境（即 http://localhost:8000）`，点击运行设计好的接口用例。
  * **后端 API 极速排错 (辅助)**：访问 `http://localhost:8000/docs`（FastAPI 自动生成的 Swagger），排查 Schema 模型字段是否写错。
  * **数据库管理**：使用 **Navicat** 连接本地 MySQL（Host：`localhost`，端口：`3306`，用户：`root`，密码：在 `.env` 中查看），直观查看数据表结构变化。

* **第五步：提交前强制自测清单**：
  在进入第 5 步（提交代码）之前，必须确保以下三点全部通过：
  * **容器存活检查**：执行 `docker ps`，确认 `liteknow-backend-dev` 和 `liteknow-mysql-dev` 的状态都是 `Up`。
  * **契约对齐**：使用 **Apifox** 向本地后端发送测试请求，必须返回 `200 OK` 且数据结构完全符合 API 文档设计。
  * **无异常日志**：执行 `docker logs --tail 50 liteknow-backend-dev`，确认刚才的接口调用没有导致 Python 抛出 `500` 内部错误或大段的异常堆栈。

* **第五步：容器重载与环境排障 (四级机制)**：
  在日常开发中，请严格根据变动的内容，选择对应的 Docker 重载级别。

  | 重载级别                                   | 触发场景                                        | 操作指令                                                                                                                                                                   | 耗时预期 |
  | :----------------------------------------- | :---------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------- |
  | **🟢 级别 0：自动热重载**                   | 修改业务代码 (`.py`) 或替换静态模型文件         | **无需指令**。保存后 Uvicorn 会通过挂载卷自动捕捉变化并重启进程。                                                                                                          | < 1 秒   |
  | **🟡 级别 1：普通重启**                     | 服务假死、修改了端口映射、需重连本地数据库      | `docker-compose -f docker-compose.dev.yml restart backend`                                                                                                                 | ~ 3 秒   |
  | **🟠 级别 2：标准构建**<br>*(最常用)*       | 更新了 `requirements.txt` 或修改了 `Dockerfile` | `docker-compose -f docker-compose.dev.yml down`<br>`docker-compose -f docker-compose.dev.yml up -d --build`                                                                | ~ 30 秒  |
  | **🔴 级别 3：终极重置**<br>*(无缓存核武器)* | 遭遇“幽灵Bug”（代码未改但报错）、需清理臃肿缓存 | `docker-compose -f docker-compose.dev.yml down`<br>`docker-compose -f docker-compose.dev.yml build --no-cache backend`<br>`docker-compose -f docker-compose.dev.yml up -d` | > 5 分钟 |

## 5. 提交验收：推送代码与发起 PR

本地测试通过后，需将代码推送至 GitHub，并交由经理与 QC 进行双重验收。

* **第一步**：将改动添加到暂存区并提交。Commit Message 必须关联 Issue 编号。
  ```bash
  git add .
  git commit -m "feat: 新增教育助手智能任务分解功能 (#IHOKNE)"
  ```
* **第二步**：将本地最新代码推送至云端。由于在创建分支时已经建立了追踪关系，后续每次推送只需执行最简命令。
  ```bash
  git push
  ```
* **第三步**：前往 **GitHub** 网页端，发起从当前分支合并至 `main` 分支的 **Pull Request (代码评审)**。
* **第四步**：指派经理进行代码 Review，指派 QC 进行拉取测试。验收通过后，此 Issue 将自动关闭。完成合并后，请及时清理本地临时分支。

> **💡 特别提醒（关于 Alembic 的协作）**：
> 当其他队友（或经理）在 GitHub 上合并了你的数据库变更 PR（包含迁移文件）后，他们拉取代码时必须执行 **第 4 步中的“第二步”**（`alembic upgrade head`），否则他们的本地 MySQL 将无法匹配最新的数据模型，导致程序崩溃。这点请务必在每日站会中着重提醒团队。
