# 轻知 (LiteKnow) 详细接口规范说明文档

### 一、 响应报文基础结构

所有 API 接口（无论成功与否）均统一返回以下 JSON 外壳格式，前端通过解析 `code` 与 `success` 字段进行第一层逻辑分发。（**注**：此通用外壳结构已在 `Apifox` 项目的“**默认响应模板**”中配置完毕。大家后续新建接口时系统会自动套用，无需手动重复拼装。）

```json
{
  "code": 200,          // 状态码（详见下表）
  "success": true,      // 快速判断位 (true/false)
  "message": "请求成功", // 提示信息（直接用于前端弹窗或 UI 引导）
  "data": {}            // 业务数据载体（异常时通常为 null 或 {}）
}
```
> **特例声明 (OAuth2 兼容)：**
> 仅有 **PC 管理后台的登录接口 (`/api/v1/admin/login`)** 为特例。为了兼容 Swagger UI 及标准 OAuth2 协议，该接口不使用上述 `ResponseModel` 外壳，而是直接返回扁平字典：
> ```json
> {
>   "access_token": "eyJhbG...",
>   "token_type": "bearer",
>   "role": "admin",
>   "nickname": "管理员"
> }
> ```
> 前端在编写拦截器时，请针对 `/login` 路径做好特殊放行处理。

### 二、 状态码大纲定义

为便于异常溯源，状态码分为 **HTTP 标准状态码 (三位数)** 与 **业务自定义状态码 (五位数)** 两类：

  * **`200`**：请求成功且业务逻辑正常。
  * **`4xx / 5xx` (标准网络/协议级错误)**：
      * **`400`**：传参错误或账号密码验证失败。
      * **`401`**：未授权，Token 缺失或已过期，前端需跳转登录页。
      * **`403`**：禁止访问，当前账号已被封禁或权限不足。
      * **`404`**：请求的路由或资源不存在。
      * **`422`**：FastAPI 底层数据校验失败（格式不对、缺少必填字段等）。
      * **`500`**：服务器内部发生未被捕获的致命崩溃。
  * **`1xxxx`**：

### 三、 标准异常提示文案规范 (HttpErrMsg 与 ErrorCode)

为了避免后端代码中出现硬编码的“魔法字符串（Magic Strings）”，并保证前端捕获到的错误弹窗提示语（`message` 字段）绝对统一，系统后端的异常抛出严格区分为以下两套体系：

#### 1. 协议级/网络级异常 (使用 `HttpErrMsg` 常量)
针对 FastAPI 框架底层的拦截、OAuth2 规范的登录失败、路由不存在等**标准 HTTP 错误（状态码 4xx/5xx）**，后端统一抛出 `HTTPException`，并强制配合 `HttpErrMsg` 常量类作为提示文案。

**后端 `HttpErrMsg` 常量字典表：**


> **后端开发须知：**
> 在编写 `/login` 接口或 JWT 鉴权依赖拦截器时，严禁直接手写中文提示，必须这样调用：
> `raise HTTPException(status_code=400, detail=HttpErrMsg.LOGIN_FAILED)`


#### 2. 纯业务逻辑异常 (使用 `ErrorCode` 枚举)

针对具体的业务流程卡点（如：图片质量太低、三级检索未命中、图书重复添加等），HTTP 网络状态码统一返回 `200 OK`，但在响应报文的 JSON 中返回 `1xxxx ~ 5xxxx` 的自定义业务码，并严格配套使用 `ErrorCode` 枚举抛出异常。

> **后端开发须知：**
> 在绝大多数常规 CRUD 业务中，严禁抛出 FastAPI 自带的 `HTTPException`。必须使用我们自定义的业务异常类，并通过调用预定义的枚举值进行抛出（系统底层会自动从 `ERROR_MESSAGES` 字典中获取对应的提示语）：
> `raise CustomAPIException(code=ErrorCode.BOOK_NOT_FOUND)`
> 
> *(注：如果确需覆盖默认提示语，可手动传入 `message` 参数：`raise CustomAPIException(code=ErrorCode.BOOK_NOT_FOUND, message="自定义的找不到提示")`)*

### 四、 核心业务级错误码详细定义

为确保 API 响应的确定性与前端异常捕获的一致性，系统定义了 `1xxxx` 至 `3xxxx` 五位数的业务状态码。所有业务异常响应的 HTTP 状态码均为 `200 OK`，实际错误详情通过 JSON 报文中的 `code` 与 `message` 字段承载。

> **开发指南：** 任何涉及业务逻辑中断的代码逻辑，严禁直接 `raise HTTPException` 或返回自定义错误数据结构。必须统一使用 `raise CustomAPIException(code=ErrorCode.XXX)`。系统底层拦截器会自动将其序列化为标准契约格式，并确保响应报文统一性。

### 五、 核心业务参数约束


在具体的核心接口中，必须强制校验以下入参：

| 参数名           | 类型        | 业务约束与说明                                                                                                                                                                                                                                                         |
| :---------------:  | :---: | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `device_id`      | String        |**设备唯一标识**。由于系统免登录，必须依靠前端生成并缓存在 LocalStorage 的 UUID 作为用户标识，用于后端的并发限流（防连拍）和日志追踪。                                                                                                         |
| `search_keyword` | String       | **用户搜索意图**。即用户输入的书名或 ISBN 。                                                                                                                                                                                                    |
| `image_blob`     | File (Binary) | **截帧图像流**。前端利用 Canvas 压缩后的二进制流。<br>• **硬性限制：** 单张图片体积必须 **≤ 150KB**，以适配 10M 带宽。<br>• **尺寸限制：** 最长边强制重采样为 **1280px**。 |
| `retry_count`    | Integer       | **重试计步器**。默认为 0。当触发 `30004` 等重试策略时，前端携带此参数累加，以便后端判定是否需要执行降级（如跳过 OpenCV 增强）。                                                                                                                 |

### 六、 请求协议与 Header 规范

根据前端调用的终端不同，Header 规范分为两套机制：

**1. C端：WebAR 移动端（免登录流）**
* 不校验用户身份，无需 Token。
* 必须在请求头中携带设备指纹：`X-Device-ID: <生成的UUID>`（用于并发排队限流和日志追踪）。

**2. B端：PC 管理后台（强鉴权流）**
* 除登录接口外，所有 `/api/v1/admin/*` 路径下的接口均为保护路由。
* 请求头必须携带 JWT 令牌：
  ```http
  Authorization: Bearer <通过 /login 获取的 access_token>
  ```

### 七、 接口版本控制与路径规范

为了保障“书途”项目后续的平滑迭代，并对齐业界主流的 RESTful API 设计规范，本项目统一采用 **URL 路径版本控制（URI Versioning）**。考虑到目前我们正处于单机闭环验证（MVP）阶段，具体的路由环境规范如下：

* **基础路径 (Base URL)：** 统一在路由中显式声明版本号 `v1`。
  * **当前本地开发阶段：** 统一使用本地环回地址 `http://127.0.0.1:8000/api/v1` 或 `http://localhost:8000/api/v1`。
    * *(注：浏览器将 `localhost` 默认视为安全上下文。这意味着我们在前端调用手机摄像头 `getUserMedia` 截取书架视频流时，直接用 HTTP 即可，完全不需要去配置复杂的 HTTPS 证书，大家可以直接跑通核心业务流！)*
  * **未来上云部署阶段：** 待正式购买服务器并在宿主机跑通后，统一替换为服务器局域网 IP、公网 IP 或具体域名。

* **模块划分规则（按业务域解耦）：**
  * **视觉感知与定位模块：** `/api/v1/cv/...` 
  * **图书数据检索模块：** `/api/v1/book/...` 

* **前端开发规约：**
  * 前端同学在初始化 Axios 实例时，**必须**将 `baseURL` 全局设置为包含 `v1` 的基础路径。
  * 在具体的业务组件中，只需调用相对路径（如 `request.post('/cv/detect', formData)`），**严禁**在业务逻辑中到处硬编码拼写完整的长 URL，以确保后续切换环境时只需修改一处。
